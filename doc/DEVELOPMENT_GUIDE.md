# 开发协作规程

## 当前阶段

项目当前仅建立框架。下一次开发任务应明确模块、接口与验收范围，再开始编写功能。当前源文件中的 TODO 是待实现标记，不是可运行实现。

## 每次功能开发的任务模板

```text
【项目】NEV-SmartHMI
【本次模块】填写 PRD 模块编号和目标目录
【当前状态】说明已存在的接口、相关文件与尚未确定的输入
【目标环境】X6818；附件报告 armv7l；Linux 3.4.39；Qt 5.4.1
【PC 环境】Windows；Qt 5.14.2；MSVC 2017 32-bit
【兼容约束】C++11；所有 Qt API 必须兼容 5.4.1
【界面约束】1024 × 600；Qt Widgets / QPainter；触控；暗色主题
【功能要求】列出具体输入、显示、用户操作、输出和失败状态
【接口依赖】给出协议、数据结构、信号槽和线程归属；未知项先标明
【交付文件】分别列出 .h / .cpp / QSS / 文档，避免超范围修改
【验收条件】给出正常、边界、无效数据、断连及平台验证方法
```

例如后续开发空调模块时，需列出 0.5 ℃ 调节步进、可调范围、Auto / A/C / 除雾 / 内循环按键、命令发送与状态回读。可调范围和具体 CAN 命令没有在本阶段确定，不得用示例值冒充真实协议。

## 实现与审查约定

- `.h` 与 `.cpp` 分离；业务层、UI 和硬件层保持 TECH_SPEC 中规定的职责边界。
- 所有 Qt API 以目标 Qt 5.4.1 为下限，不能以 Windows Qt 5.14.2 能编译作为兼容证明；不引入 C++14 / C++17 语法。
- GUI 更新归属主线程；后续采集、解码与阻塞 I/O 应考虑工作线程、退出和资源释放。
- 未连接设备或数据过期时提供明确状态，禁止继续把示例值显示为真实有效读数。
- 样式、图片和中文字体放到 assets，并登记来源与许可；协议和板端参数写入对应文档。
- 工具链路径、设备地址和私密凭据按本机配置管理，私钥不进入项目。

## 文档与提交

1. 需求变化更新 PRD；接口、线程、依赖或平台方案变化更新 TECH_SPEC。
2. 每次实际变更更新 CHANGELOG；发现缺陷登记 BUG_TRACKER，修复后附复现与验证结果。
3. 按修改范围进行有意义的验证。未运行的环境应标明“未验证”，不得写成通过。
4. 运行根目录 `git_commit_push.bat`，输入简明、准确的提交说明。可人工使用 `feat:`、`fix:`、`docs:` 等前缀。
5. 批处理不自动解析这些前缀或同步 Markdown；`scripts/git_commit.py` 只是预留位置。

## 后续验证范围

功能阶段至少考虑 Windows 模拟数据、Qt 5.4.1 ARM 编译、真实开发板显示与触控三类验证。摄像头、音频、CAN 与串口依赖真实设备，PC 上的模拟测试不能替代板端验证。验证记录应包含版本、输入、结果和限制。
